## Learning log for /notes write (human's questions, in order; paraphrased from chat, polish before use)
Include these in the notes, they are Java fundamentals the human wants kept (`solid`, `gof-adapter`, plus a candidate `java-records-immutability`):
- Q: What is the difference between `Finding` and `Review`? A: one issue vs the whole result of one `generate` call. A wrapper keeps the port signature frozen while the payload grows additively; an empty `Review` is a valid result (step 11 still posts "no significant issues").
- Q: Why does the generator take `ReviewContext` at all? A: the spec does not say what the adapter uses it for (E5 decides). It reserves a slot so the frozen signature never changes. Tension with Interface Segregation (unused fields) vs a frozen seam. `ReviewContext` is the label of the job, not the diff.
- Q: Who chooses `min_severity`? A: the repo owner, in `.reviewbot.yml` (§7.1 step 7); missing or unparsable file falls back to defaults. Default value not found in the spec sections searched (probably E1-5).
- Misconception fixed: "above" means more severe, not a bigger number. With `CRITICAL` first, ordinal falls as severity rises, which is why a first attempt `min.ordinal() <= ordinal()` was backwards. The human then reversed the order so "higher number = more severe". Order and operator must change together; a test table guards it.
- Q: If `Review` is immutable, how does step 11 drop findings? A: it does not remove anything; it builds a NEW `Review` from a filtered list, and the original stays (useful for "4 returned, 2 kept" logging).
- Q: Aren't records immutable already? A: yes, but shallow. Fields are final; the envelope is fully immutable because all its components are immutable types. A `List` component is mutable, so `Review` needs `List.copyOf` in its compact constructor (also rejects null elements). Check each record component: can it be changed from inside?
