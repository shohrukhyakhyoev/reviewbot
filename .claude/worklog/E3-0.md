## Learning log (the human's questions this session; for `/notes write spring-boot`)
- Why cache the request? A body is a one-shot stream. `CachedBodyHttpServletRequest` reads the bytes once and replays them, so the HMAC and the later JSON parse see the same raw bytes. The controller parses as usual.
- What does `chain.doFilter(x, response)` do? Hands `x` to the next stop (finally the controller); not calling it ends the request (the 401 path). Pass the wrapper, not the original.
- Own first attempts: compared the raw digest to the header text (different representations; fixed by encode-then-compare), then read the header from `response` instead of `request`.
- Register the filter how? `@Component` + `@Order` (all URLs, path check inside the filter), `@WebFilter` (no ordering), or `FilterRegistrationBean` (path and order declared together; chosen). The filter is deliberately not a bean.
- Who calls `GatewayConfig.hmacVerificationFilter(...)`? Spring, once at startup. Parameters are resolved by type from the container (`SignatureVerifier` is a scanned `@Component`; `GatewayProperties` comes from `@EnableConfigurationProperties`). The method name is the bean name.
- How does the 25 MB reach the code? yaml/env (optional) -> `@DefaultValue("25MB")` -> `GatewayProperties` -> `GatewayConfig` -> `new HmacVerificationFilter(verifier, int)` -> `new CachedBodyHttpServletRequest(request, int)`. The filter and wrapper are not beans, so the config class hands the value down through plain constructors.
- How do we pass only the props a class needs (R5, ISP)? The `@Bean` method in `GatewayConfig` takes the whole `GatewayProperties`, picks the field (`properties.webhookSecret()`, `properties.maxBodyBytes()`) and hands only that to a plain constructor. `SignatureVerifier` is now declared there, no longer a `@Component`, so `webhook` imports nothing from `config`.
- IntelliJ "not annotated parameter overrides @NonNullApi": no nullability policy in the repo (ADR candidate above).
