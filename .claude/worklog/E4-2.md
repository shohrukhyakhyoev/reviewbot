## Decisions pending (ADR candidates)
- 2026-11-21 (R19, skipped nit, per the human's stop-after-nits rule): a flag a handler restores after returning stays set into the next job (an unearned TRANSIENT retry hop; strayInterruptCleared names the next record). Folds into the interrupt-policy ADR for E4-3/E4-4: decide whether to clear before each job too, or stop on interrupt.
- 2026-11-21 (R15): drainer interrupt policy. An interrupt is not a stop signal for a drainer: the job's failure is classified (TRANSIENT), the flag is cleared before the outcome handler, and the record completes normally. Shutdown is §12's stop-intake-and-wait owned by E4-3/E4-4. Concurrency/failure handling → ADR candidate (E4-3/E4-4 may revisit with executor close semantics).
- 2026-11-21 (R1, fixed by Claude at the human's request): the drainer owns `markComplete`. `CompletionHandler` (handler ends in markComplete) became `OutcomeHandler.handle(ConsumerRecord, Outcome)`: it never sees the `TrackedOffset`, and `Drainer.complete` calls `markComplete` exactly once after it returns or throws. Reason: OffsetTracker releases a zombie's permit on every call (no duplicate detection after re-register/unregister, I7), so a handler that completed and then threw made the old fallback over-release. Matches spec §8.3 (`complete(job, outcome); // outcome handler §7.2 + markComplete`); the ticket's wording "whose contract ends in markComplete" is superseded (spec wins). E5's §7.2 handler implements `OutcomeHandler`; I9 order holds (handler produces, then the drainer completes). Delivery/failure semantics → ADR candidate.
- 2026-11-21 (R3, Claude, human chose option b): route() on a closed partition reports `EngineMetrics.routedToClosedPartition` and still enqueues; no Java `assert` (off in production; in tests it would add an uncovered branch below the engine gate). Detection belongs to E4-3: its poller tests must assert `closedPartitionRoutes` stays empty. → PROGRESS key decision + Deferred for E4-3 at close.
- 2026-11-21: catch-all width. Human wrote `catch (Exception)`; at the human's request Claude widened both to `Throwable` (an `Error` such as `StackOverflowError` would kill the drainer and strand the PR; OOM handled by `-XX:+ExitOnOutOfMemoryError`, PROGRESS deferred). Pinned by `DrainerTest.anErrorFromAJobIsClassifiedLikeAnyOtherFailure`. Failure handling → ADR candidate.
- 2026-11-21 (human's question): a throw inside `route()` (bad Kafka key → `PrKey.parse` IAE; executor shut down → `RejectedExecutionException`) reaches the poller thread; the record already holds a permit + `TrackedOffset`. Spec is silent (§8.2 only shows `PrKey.of(r)`). Who completes it (poller via handler as poison, vs dispatcher)? Failure handling → ADR candidate.
